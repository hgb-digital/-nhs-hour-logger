NHS Hour Logger Guide
Hudson Brackeen
Uploaded for the MIT Maker Portfolio

#--Description--#
This logger was created to centralize all NHS organization into one website. This logger, however, never reached deployment due to strict FERPA guidelines, which place strict limitations on the hosting of student information. Although I made multiple efforts to work with our local district IT, we never reached an agreement. This logger serves as a template for an organizational volunteer web app, proving viability of future use with local volunteer organizations (especially since it's light weight). 
#--#

#--Development--#
To develop this web app, I ran a XAMPP development webserver (including Apache and a MySQL database) and coded using Visual Studio Code. I mainly used Claude for research purposes, helping me to continue to learn the languages (PHP, HTML, CSS, JS, MySQL) and brainstorm technical workarounds. Throughout the process, I met with my chapter advisor to discuss the future direction of development in order to fit the needs of the organization.

A MySQL configuration file for the NHS database is also included in this repository. The majority of the information included in that database was generated by Claude for filler data so I could see how it would look while in use. 
#--#

#--Features--#
Users can log in, log hours, signup for service opportunities, and see hour statistics per committee. At my high school we have 4 committees within NHS (everyone is a member of one) that each focus on differing avenues of service. Officers can also create service opportunities (title and description) and add as many roles as needed. Roles can have a title, a time of service, an attire, and a set number of signup slots. When logging hours, users can add either Individual Service Projects (ISPs) or Group Service Projects (GSPs). Individual hours require a supervisor while group service hours require you to have been signed up on the service sheet prior to the date of service. Officers can also remove hours they feel are malicious or incorrectly documented.

#--Process/Structure--#
This project was developed over 2 weeks and, alongside other projects, was uploaded to Github for the MIT Maker Portfolio and therefore have minimal version control. However, below I have outlined the development process so reviewers can specifically see how the project evolved over time. Information regarding development will also be provided in the media upload of the MIT Maker Portfolio.

*PHASE 0*: In April 2026, before starting the project, I met with my chapter advisor to see if an NHS website would be used and got approval to start development.

*PHASE 1*: For this project, I began by using the same login/signup system along with the basic structure for a website that I used in the Eversole Network project (see other projects). This structure worked as follows:

File Segmentation: Project files are split into 2 folders: htdocs and private. The folder htdocs was the web root and was what web users physically had access to from the internet. However, in order to create a secure environment, I moved the majority of the project's files into a private folder (inaccessible to web users). The index.php in the htdocs folder would then check the URL the user inputted (or was directed to) and ensure the file they were trying to reach was accessible with the permissions they were assigned at login. For this project, I simply checked if the user was logged in before allowing them to access the url they were requesting (assuming the file existed). For each admin or officer specific pages, there was a permission check at the top of the file and redirected the user if they didn't meet the permissions.

File Organization: In the private folder, I split each file into different groups based on function. The pages/all_access folder simply contained all the pages I allowed users to navigate to through the URL (through index.php). The scripts folder contained everything else. The features folder contained PHP $_SESSION config (how login is stored) and a functions script which had miscellaneous functions that could be called by others scripts. The login and signup folders had scripts for user login and signup, respectively. The view folder contained scripts having to do with tables, images, messages, or CSS (see serve_resources section below). The web management folder contained scripts that could be accessed using POST requests (see handle_POST section).

Database Queries: The dbh_manager.php file (in /private) handled all database queries. Using this file, scripts could simply run the run_query() function in order to grab information from the database. An important security feature, this file used statement preparation with variables bound to the statement rather than injected. This prevented SQL injection by checking each user input (username, password, etc.) before attaching it to the SQL query. 

handle_POST: There are a variety of forms that need to submit data through POST requests, however these scripts are hidden in the private folder and therefore HTML cannot access them in the <form> action parameter. Therefore, I created the handle_POST.php file in the htdocs (public) directory for handling POST requests. Any form attempting to make a post request (like logging in) will send data to this file and it will then evaluate whether or not the user has sufficient permissions to make the request (actions such as logging hours require the user to be logged in). Because there are ways to submit POST request without being on the actual webpage, this file acts as a barrier for users attempting to access functions they are not authorized to access. 

serve_resources: Similarly to POST requests, sometimes a file needs to reference CSS files, images, or Javascript files that are not available in the public htdocs directory. The file simply allows HTML to use resources found in the private folder (specifically /private/view/resources). 

*Phase 2*: I now needed to alter the previous architecture to fit the needs of the NHS. In general, this included altering the user permissions enumerable in the database, creating hour log/signup sheet tables in the database, and rebranding the colors/text to fit NHS.

*Phase 3*: This is when new development started. I first began with the hour logging system. In NHS, we have both individual and group hours (outlined above) so I needed a system that could allow users to log both. When users access the Log Hours pages, the first thing displayed is the number of ISP (individual) vs. GSP (group) hours they have logged. The second section is where they can log hours. Here, there is a toggle of whether they'd like to log group or individual hours. The last 2 sections simply display what hours you've already logged and allows you to remove them. 

*Phase 4*: A key part of NHS is group hour opportunities where NHS members all volunteer together. These opportunities require a signup sheet so the organizers know who to expect and the officers know who to expect to log group hours. I implemented this into my logger. On the Group Service page, members can view upcoming and past volunteer opportunities. Clicking on upcoming signups allows them to add their name to the list as well as remove their name if necessary. Officers can create these signup sheets, assigning different roles and slots as necessary. In order to prevent forgery of hours, users can only log group hours from opportunities in which their name has been added (the website provides a dropdown of what hours you are permitted to log). 

*Phase 5*: This was the final development phase. I allowed users to view a list of all NHS members as well as the hours they've logged. Users could also click on the names of the members to see all the hours they've logged. Officers had the ability to delete hours they felt were malicious. Lastly, I used Claude to help create an hour chart that displayed hour statistics (number of hours logged) by each committee.

*Phase 6*: This is sadly where development ended. After creating this functional prototype, I wished to move on with production but our local IT department did not grant permission for me to host student information due to compliance constraints with FERPA. I tried to negotiate by hosting with an IT approved partner (AWS) but I was never granted permission.
